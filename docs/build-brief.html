01 / What we're building

The smallest useful product.

This brief is the first shippable cut of DealDesk. It is not the full dev spec — it is the minimum version that an investor can pay for, log into, get value from on day one, and stay subscribed to. Everything else (BRRR & HMO engines, branded packs, partner marketplace, SMS alerts, comparison view, admin console depth) is explicitly deferred and bolts on top of the same core.

The user journey we're shipping

  1. Investor signs up with email + password.
  2. Picks a plan, pays via Stripe, gets 14-day Pro trial.
  3. Lands on the dashboard. Sees a unified feed of properties from Rightmove, Zoopla, and Purplebricks.
  4. Filters the feed: postcode, price range, bedrooms, property type, minimum yield.
  5. Adds interesting properties to a watchlist.
  6. From the watchlist, clicks into the deal analyzer page for any property.
  7. Sees a BTL pass/fail verdict with the four key numbers (cash required, cashflow, ROI, gross yield) and a +2% stress test result.

What that specifically includes

Definitely in scope

  • Email + password login (Clerk)
  • Stripe Checkout, 3 plans (Starter / Pro / Elite), self-service Customer Portal, webhooks
  • Manual URL ingestion + one commercial aggregator feed for property data
  • Unified dashboard list of properties with filters
  • Per-user watchlist (add / remove / view)
  • Single deal analyzer page — BTL only
  • Pass/fail verdict with explainable reasons
  • +2% stress test (single scenario for MVP)
  • Mobile-first responsive web (PWA install banner is fine; native app deferred)

Explicitly out of scope for v1

  • BRRR / HMO / SA / flip engines (BTL only)
  • Side-by-side deal comparisons
  • Branded investor pack PDF generation
  • Pipeline / kanban
  • SMS alerts (email-only is fine for v1; alerts are deferred entirely)
  • Partner marketplace and partner portal
  • Team seats / workspaces (single-user accounts only)
  • AI narrative summaries
  • Native iOS / Android apps
  • Admin console depth (basic Supabase studio access is fine)
The discipline

If a feature isn't on the "definitely in scope" list, it doesn't ship in v1. Every "while we're at it" addition is a week of slip. The full dev spec lists 16 sections of features — this brief intentionally covers ~30% of them. The shape of the architecture (Section 02) is what makes the other 70% cheap to add later.

02 / Bolt-on architecture principles

Build for tomorrow's features, today.

The single most important property of this codebase is that adding a feature in 6 months should not require rewriting what we ship in 12 weeks. Six concrete principles enforce that.

The six principles

PrincipleWhat it means in code
1. Feature-folder modularity Every feature lives in its own folder under /features/{name} with its own routes, components, server logic, and tests. New features (packs, comparisons, partners) are new folders, not edits to existing ones.
2. Feed adapters via interface All property data sources implement a single PropertyFeedAdapter interface. Rightmove, Zoopla, Purplebricks, manual paste, and any future source plug into the same shape. Adding a new source is one new file.
3. Strategy engines as plugins The MVP ships with one strategy engine (btl). Engines implement a StrategyEngine interface. Adding BRRR / HMO / flip / SA is registering a new engine in the registry — no changes to the dashboard, watchlist, or analyzer page wiring.
4. Entitlements behind one function Plan-gated features check getEntitlements(userId). Never inline plan logic. Adding a "comparisons require Pro" rule in 4 months is one new boolean on the entitlements object.
5. Append-only deal results Analyzer output writes a new deal_results row each time. Re-running never updates. This unlocks pack regeneration, comparison view, and audit trails later — for free.
6. Event-driven hooks Domain events (property.ingested, deal.analysed, watchlist.added) are emitted from day one even if nothing consumes them. Future features (alerts, packs, partner routing) subscribe — never bolt patched into the source flow.

The architectural test

During code review, ask: "If we wanted to add the next feature from the dev spec next week, would we have to change this code?" If yes, refactor before merging. The cost of getting this right in week 1 is hours; the cost of getting it wrong is months.

04 / Auth & user accounts

Sign up. Sign in. Done.

Auth is solved by Clerk. Don't build it. The job here is to wire Clerk into Next.js correctly, define the minimum role model, and make sure every API call is scoped to the authenticated user.

What ships in v1

  • Sign-up flow: email + password, immediate email verification, redirect to /onboarding/plan.
  • Sign-in flow: email + password with magic-link fallback for password recovery.
  • 2FA: available, optional in v1. Required for any user with role admin.
  • Sessions: 30-day expiry on web, sliding renewal on activity.
  • Roles: two only — user (everyone) and admin (founder + future ops staff). Workspaces and team seats are deferred.
  • Settings page: change email, change password, enable 2FA, delete account (soft-delete + 30-day grace).

Wiring rules

// every authed page is wrapped
// app/(authed)/layout.tsx
import { auth } from '@clerk/nextjs/server';
export default async function AuthedLayout({ children }) {
  const { userId } = await auth();
  if (!userId) redirect('/sign-in');
  return <>{children}</>;
}

// every API route validates
// app/api/watchlist/route.ts
import { auth } from '@clerk/nextjs/server';
export async function GET() {
  const { userId } = await auth();
  if (!userId) return new Response('Unauthorized', { status: 401 });
  // every db query goes through the user's RLS context
  const list = await db.query.watchlist.findMany({
    where: eq(watchlist.userId, userId),
  });
  return Response.json(list);
}

The local user record

Clerk owns the identity; we own the local user row that joins identity to subscription, watchlist, and deals. A Clerk webhook syncs:

// On user.created (Clerk webhook)

// On user.updated → keep email + name in sync
// On user.deleted → soft-delete locally, retain row for audit + cancellation flow
Don't skip

Set up the Clerk webhook handler in week 1. Every other feature assumes the local users row exists. If it doesn't get created automatically, sign-up appears to work and then everything else 500s.

The single entitlements function

Every plan check in the codebase goes through this. Inline plan logic anywhere else is a code review block.

// lib/entitlements.ts
export type Plan = 'starter' | 'pro' | 'elite' | 'free';

export type Entitlements = {
  plan: Plan;
  trial: boolean;
  // MVP-relevant flags only
  maxSavedDeals: number;       // starter:10  pro:Infinity  elite:Infinity
  maxWatchlistItems: number;   // starter:25  pro:200       elite:Infinity
  // Stubbed for future features — false in MVP, no UI yet

  canCompare: boolean;
  canExportPack: boolean;
  canUseHMO: boolean;
  teamSeats: number;           // 1 for everyone in MVP
};

export async function getEntitlements(userId: string): Promise<Entitlements> {
  const sub = await db.query.subscriptions.findFirst({
    where: eq(subscriptions.userId, userId),
  });
  return mapPlanToEntitlements(sub?.plan ?? 'free', sub);
}

The trial → paid → cancelled flow

  1. User picks plan on /onboarding/plan → Stripe Checkout with trial_period_days=14.
  2. Returns to /onboarding/welcome on success.
  3. 13 days later: Resend sends "your trial ends tomorrow" via trial_will_end webhook.
  4. If they cancel before period end: subscription stays active until end of period, then read-only access for 30 days, then full delete.
  5. If payment fails: 3 retries (Stripe default), each retry triggers a dunning email; final failure → read-only.
Webhook idempotency is not optional

Stripe will, occasionally, send the same event twice. If the handler is not idempotent, you get duplicate subscription rows, double-counted activations, and weird state. Use stripe_event_id as a unique key. First check: have we seen this event? If yes, return 200 immediately. Test this with the Stripe CLI's --forward-to + manual replay.

06 / The unified property feed

One dashboard. Many sources.

This is the centre of gravity of the MVP. The user wants to open one screen and see properties from Rightmove, Zoopla, and Purplebricks in a single filterable list. Behind the scenes, that means a feed-adapter pattern with three (or more) sources writing into one canonical properties table.

The honest reality of UK property data

Rightmove and Zoopla do not publish open APIs to ingest their entire feed. Their data is available to:

  • Estate agent partners via portal-feed agreements (we don't qualify).
  • Commercial aggregators who license normalised data — PropertyData, Yomdel, Move iQ, OpenBrix, Property Filter and similar (we pay them; they have the agreements).
  • The portals' own consumer search pages via on-demand fetch of a single listing URL the user pastes (legitimate single-page fetch with caching).

Purplebricks listings are syndicated to Zoopla and (to a lesser extent) Rightmove, so coverage from a commercial aggregator typically includes them by default.

The MVP feed strategy

SourceMethodCoverageMVP status
PropertyData Commercial API, ~£150–£250/mo UK-wide BTL listings, sales prices, rental comps, postcode statistics Primary ingestion source
Manual URL paste User pastes a Rightmove / Zoopla / Purplebricks listing URL → server fetches once, parses, stores Any single property the user finds anywhere Secondary "import this one" path
Rightmove direct feed Portal-feed agreement Best coverage Deferred — pursue in parallel with launch
Zoopla partner API Zoopla developer programme Good coverage Deferred — apply day one, may take months

The point is the architecture: any source we add later (Rightmove direct, Zoopla partner, OnTheMarket, PrimeLocation, off-market sourcer feeds) becomes one new file under /features/properties/adapters implementing the same interface.

The adapter interface

// features/properties/adapters/_interface.ts
export interface PropertyFeedAdapter {
  /** Stable identifier for this source, e.g. 'rightmove' */
  source: string;

  /** Either provides batch listings (PropertyData, Zoopla partner)... */
  fetchBatch?(since: Date): Promise<RawListing[]>;

  /** ...or fetches a single listing from a URL (manual paste path) */
  fetchOne?(url: string): Promise<RawListing>;

  /** Parses raw source data into our normalised shape */
  normalise(raw: RawListing): NormalisedProperty;
}

export type NormalisedProperty = {
  source: string;
  source_listing_id: string;
  source_url: string;
  address_line_1: string;
  postcode: string;
  city: string | null;
  county: string | null;
  latitude: number | null;
  longitude: number | null;
  property_type: 'flat' | 'terrace' | 'semi' | 'detached' | 'other';
  bedrooms: number;
  bathrooms: number | null;
  floor_area_m2: number | null;
  tenure: 'freehold' | 'leasehold' | 'unknown';
  epc_rating: string | null;
  listing_price: number;        // pence
  listing_status: 'active' | 'under_offer' | 'sstc' | 'withdrawn';
  listed_at: Date;
  raw_payload: unknown;          // keep the original for debugging
};

The ingestion pipeline (Inngest)

// jobs/property-ingest.ts
inngest.createFunction(
  { id: 'properties.ingest_incremental' },
  { cron: '0 * * * *' },          // every hour
  async ({ step }) =>; {
    for (const adapter of registeredBatchAdapters) {
      const raw = await step.run(`fetch-${adapter.source}`,
        () => adapter.fetchBatch(lastRunFor(adapter.source)));
      await step.run(`upsert-${adapter.source}`,
        () => upsertProperties(raw.map(adapter.normalise)));
      await step.run(`emit-${adapter.source}`,
        () => emit('property.ingested', { source: adapter.source, count: raw.length }));
    }
  }
);

// jobs/property-paste.ts (event-driven, fires on UI paste)
inngest.createFunction(
  { id: 'properties.fetch_one' },
  { event: 'property.paste_requested' },
  async ({ event, step }) =>; {
    const adapter = pickAdapterForUrl(event.data.url);
    const raw = await step.run('fetch', () => adapter.fetchOne(event.data.url));
    const property = adapter.normalise(raw);
    await step.run('upsert', () => upsertProperty(property));
    await step.run('emit', () => emit('property.ingested', { source: adapter.source, count: 1 }));
  }
);

Deduplication — one address, many listings

The same property can appear in PropertyData and on a manually-pasted Rightmove URL. The canonical properties table holds one row per real-world address; property_listings holds the per-source snapshots. Dedup key is normalised address + postcode (postcode normalised to UPPER + space-stripped). Postcode comes from postcodes.io, not the source — sources lie about postcodes.

Build order for feeds

Week 1: build the manual-paste adapter for a single Rightmove URL. This is testable end-to-end with no commercial agreement required. Week 3: integrate PropertyData. Week 5+: pursue Zoopla / Rightmove direct in parallel — they don't block launch.

07 / Dashboard with filters

The screen the user opens daily.

The dashboard is the single most important UI in the MVP. Every retention metric flows through it. Show recent listings from all sources, applied user filters, with the watchlist and deal-analyzer entry points one tap away.

Layout (mobile-first, 360px viewport)

  • Header bar: greeting + plan badge + settings icon.
  • Filter bar (sticky): postcode / area, price range, bedrooms, property type, minimum gross yield. Saved filter chip if one is active.
  • Results list: vertically stacked cards. Each card shows address line + postcode, price, bedrooms, source pill (Rightmove / Zoopla / Purplebricks), gross yield estimate, "+ Watchlist" button, tap to open deal analyzer.
  • Empty state: "No properties match your filters" + suggested tweak.
  • Footer: tab bar (Home · Search · Watchlist · Settings).

Filter contract

// types/filters.ts
export type PropertyFilter = {
  postcodeArea?: string;        // e.g. 'PE1', 'PE', or full postcode
  radiusMiles?: number;          // optional radius around postcode centroid
  priceMin?: number;            // pence
  priceMax?: number;
  bedroomsMin?: number;
  bedroomsMax?: number;
  propertyType?: ('flat' | 'terrace' | 'semi' | 'detached')[];
  minGrossYield?: number;        // 0.07 = 7%
  sources?: string[];            // ['rightmove', 'zoopla', 'purplebricks']

  sortBy?: 'newest' | 'priceAsc' | 'priceDesc' | 'yieldDesc';
  page?: number;
  pageSize?: number;             // default 20
};

The query

Postgres handles this comfortably for a single-region launch. Indexes on postcode, listing_price, bedrooms, status. Gross-yield filter requires a small denormalised estimated_gross_yield column on the property row (computed at ingest using the area's average rent from PropertyData; refreshed on listing update).

// features/properties/queries.ts
export async function searchProperties(
  userId: string,
  filter: PropertyFilter,
): Promise<PropertySearchResult> {
  // RLS context not strictly needed (properties are global),
  // but query joins to user-specific watchlist flag
  return db.execute(sql`
    select p.*,
           exists(
             select 1 from watchlist w
             where w.user_id = ${userId} and w.property_id = p.id
           ) as on_watchlist
    from properties p
    where p.status = ${filter.status ?? 'active'}
      and (${filter.postcodeArea}::text is null
           or p.postcode like ${filter.postcodeArea + '%'})
      and (${filter.priceMin}::int is null
           or p.listing_price >= ${filter.priceMin})
      and (${filter.priceMax}::int is null
           or p.listing_price <= ${filter.priceMax})
      and (${filter.bedroomsMin}::int is null
           or p.bedrooms >= ${filter.bedroomsMin})
      and (${filter.minGrossYield}::numeric is null
           or p.estimated_gross_yield >= ${filter.minGrossYield})
    order by ${orderBy(filter.sortBy)}
    limit ${filter.pageSize ?? 20}
    offset ${(filter.page ?? 0) * (filter.pageSize ?? 20)}
  `);
}

08 / Watchlist

The bridge from browse to analyse.

The watchlist is small in code but central in product. It is where users park properties they're interested in but haven't analysed yet. Every property on the watchlist is one tap from the deal analyzer page.

What the user can do

  • From any property card on the dashboard: tap "+ Watchlist" → property is added.
  • Watchlist tab shows a vertical list of saved properties with source, price, address, date added.
  • Each item has "Analyse" (opens deal analyzer) and "Remove".
  • Sort by date added (default), price, or postcode.
  • Optional note per watchlist item (free text, 280 chars) — surfaced as a subtitle on the card.
  • Plan limits enforced via entitlements: Starter 25 items, Pro 200, Elite unlimited.

Data shape

What "Analyse" does

Tapping Analyse on a watchlist item is a server action that:

  1. Looks up or creates a deals row for this user + property + strategy btl.
  2. Runs the BTL engine (Section 09) against the user's saved assumption profile (or default profile if none saved yet).
  3. Inserts a fresh deal_results row.
  4. Redirects to /deal/[id].

This means the user never has to think about "creating a deal" — adding to watchlist and analysing it just works.

09 / Deal analyzer page

The verdict, on one screen.

The deal analyzer page is where the product earns the user's trust. It takes a property + a strategy + an assumption profile and produces a pass/fail verdict with explainable reasons, four headline numbers, and a single +2% stress test result. BTL only in v1; the engine registry from Section 02 means BRRR drops in later without changing this page.

Page layout

  • Header: address, postcode, price, source pill, "Back to Watchlist" link.
  • Verdict banner: green if pass, amber if marginal, red if fail. One sentence summary.
  • Four headline KPIs in a 2×2 grid: Cash required, Monthly cashflow, Cash-on-cash ROI, Gross yield.
  • Stress test card: today's rate vs +2% rate, monthly cashflow at each.
  • Pass/fail reasons list: every rule that was checked, with ✓ or ✗ and the actual figure.
  • Assumptions panel (collapsible): the inputs the engine used. User can edit and re-run.
  • Footer disclaimer: "Indicative analysis only. Not regulated advice."

The BTL engine — input / output contract

// features/deals/engines/btl.ts
import type { StrategyEngine } from './_interface';

export const btlEngine: StrategyEngine = {
  id: 'btl',
  version: 'btl-v1',

  run(property, assumptions, criteria) {
    // pure function, deterministic, no side effects
    const monthlyMortgage = calcMortgagePayment(
      property.listing_price * (1 - assumptions.deposit_pct),
      assumptions.rate_pct,
      25,                     // years
    );
    const grossRent  = (assumptions.rent_pcm ?? estimateRent(property)) * 12;
    const mgmtCost   = grossRent * assumptions.mgmt_pct;
    const voidCost   = grossRent * assumptions.void_pct;
    const annualCashflow = grossRent - mgmtCost - voidCost - (monthlyMortgage * 12);
    const cashRequired   = (property.listing_price * assumptions.deposit_pct)
                         + estimateStampDuty(property.listing_price)
                         + assumptions.refurb
                         + assumptions.legal_fees;
    const roi = annualCashflow / cashRequired;
    const grossYield = grossRent / property.listing_price;

    const stressRate = assumptions.rate_pct + 0.02;
    const stressCashflow = grossRent
      - mgmtCost - voidCost
      - calcMortgagePayment(
          property.listing_price * (1 - assumptions.deposit_pct),
          stressRate, 25,
        ) * 12;

    const passReasons: string[] = [];
    const failReasons: string[] = [];

    if (annualCashflow / 12 >= criteria.min_cashflow) {
      passReasons.push(`Monthly cashflow £${fmt(annualCashflow/12)} exceeds minimum £${fmt(criteria.min_cashflow)}`);
    } else {
      failReasons.push(`Monthly cashflow £${fmt(annualCashflow/12)} below minimum £${fmt(criteria.min_cashflow)}`);
    }
    if (roi >= criteria.min_roi) { /* ... */ }
    if (cashRequired <= criteria.max_cash_required) { /* ... */ }
    if (stressCashflow >= 0) {
      passReasons.push(`Survives +2% stress test`);
    } else {
      failReasons.push(`Fails +2% stress test (cashflow goes to £${fmt(stressCashflow/12)}/mo)`);
    }

    return {
      engine_version: 'btl-v1',
      outputs: {
        cash_required: cashRequired,
        annual_cashflow: annualCashflow,
        monthly_cashflow: annualCashflow / 12,
        cash_on_cash_roi: roi,
        gross_yield: grossYield,
        stress_2pct: { rate: stressRate, monthly_cashflow: stressCashflow / 12 },
      },
      pass: failReasons.length === 0,
      pass_reasons: passReasons,
      fail_reasons: failReasons,
    };
  },
};

The engine registry

// features/deals/engines/_registry.ts
import { btlEngine } from './btl';

export const engines = {
  btl: btlEngine,
  // brrr: brrrEngine,    // bolted on later — no other code changes
  // hmo:  hmoEngine,
};

export function getEngine(strategy: keyof typeof engines) {
  const e = engines[strategy];
  if (!e) throw new Error(`Unknown strategy: ${strategy}`);
  return e;
}

Versioning & reproducibility

Every run inserts a fresh deal_results row. Never update. The row stores the engine version + the full assumption snapshot, so any analysis can be re-displayed exactly as it appeared on the day. This is what unlocks the future "branded pack" feature — the pack regenerates from the result row, not from current data.

Re-running with edited assumptions

The assumptions panel on the analyzer page lets the user override any assumption inline. Re-run inserts a new result; the page swaps to display it; the previous row stays in history. v1 only shows the latest; v1.x can surface the history.

Don't ship a "score"

The temptation is to compress everything into a single 0–100 deal score. Don't. The product's value is the explanation. A user who knows why a deal failed trusts the platform; a user who just sees "62/100" doesn't. Pass / Marginal / Fail with explicit reasons. That is the user-facing contract.

13 / Acceptance criteria

How we know it's done.

v1 is shippable when every line below is true. Not before.

  • A new user can sign up, pick a plan, complete Stripe Checkout with a card, and land on the dashboard in under 90 seconds.
  • Stripe webhook is signature-verified, idempotent, and tested against duplicate-event replay via the Stripe CLI.
  • Cancelling a subscription via Customer Portal moves the workspace to read-only at end of period; this is verified end-to-end.
  • The dashboard returns ≥ 1,000 active UK properties from PropertyData ingestion within 30 days of going live.
  • A user can paste a Rightmove URL, and within 30 seconds see the property appear in their list.
  • Filters work in combination: postcode + price + bedrooms + min yield returns a reduced result set with all four constraints respected.
  • Adding to watchlist is instant (optimistic UI, server confirmation within 1 second p95).
  • Tapping "Analyse" from the watchlist returns a verdict page in under 3 seconds.
  • The BTL engine produces deterministic, reproducible output: same inputs always yield identical outputs.
  • Engine output explains pass/fail in plain English on the verdict page.
  • +2% stress test runs on every analysis.
  • Editing an assumption and re-running produces a new deal_results row; previous row is preserved.
  • Cross-tenant leak test: user A cannot read user B's watchlist, deals, or saved filters under any URL.
  • Audit log captures every state change to subscriptions, watchlist, and deals.
  • Sentry receives errors in production; PostHog receives at least 8 named events (signup, checkout_started, checkout_succeeded, property_pasted, watchlist_added, deal_analysed, filter_saved, plan_changed).
  • Accessibility: dashboard, watchlist, and analyzer pages reach Lighthouse a11y score ≥ 95.
  • Mobile: all three core pages work cleanly at 360px width, no horizontal scroll, all tap targets ≥ 44px.
  • Privacy policy + terms + cookie banner published; ICO registration completed.

Why this list matters

A common pattern in early-stage SaaS is: ship MVP, then realise that adding feature X means rewriting half the codebase. The reason is usually that the MVP wasn't built with feature X in mind. The architecture above (feature folders, adapter pattern, engine registry, event-driven hooks, append-only results, single entitlements function) is specifically designed so every item in this table is a one-folder-and-a-config-change addition — not a rewrite. Spend the time getting this right in week 1.
